# Git 提交信息规范

更新时间：2026-04-02 · 兼容 Conventional Commits · AI 友好结构化格式

---

## 1. 总体格式

```text
type(scope): summary           # 标准格式
type(scope)!: summary          # 破坏性变更，在 type(scope) 后加 !
```

- `summary` 一句话说明"做了什么"，不超过 72 字符。
- 正文使用固定段落，便于 AI/工具解析与检索：
  - `Problem` / `RootCause` / `Fix`
  - `Goal` / `Design` / `Implementation`
  - `Motivation` / `Changes` / `Behavior`
  - `Baseline` / `Optimization` / `Result`
  - `UI` / `Impact`
- `Validation` 统一拆为两个子段：
  - `Steps:` 操作步骤
  - `Result:` 验证结论

## 2. 场景模板

### 2.1 缺陷修复（fix）

```text
fix(scope): 一句话修复内容

Problem:
- <用户可见现象>

RootCause:
- <根因>

Fix:
- <改动点1>
- <改动点2>

Validation:
  Steps:
  - <复现步骤>
  Result:
  - <验证结论>
```

### 2.2 新功能（feat）

```text
feat(scope): 一句话功能描述

Goal:
- <业务目标>

Design:
- <核心设计选择>

Implementation:
- <实现点1>
- <实现点2>

Validation:
  Steps:
  - <功能验证步骤>
  Result:
  - <验证结论>
```

### 2.3 重构（refactor，无行为变化）

```text
refactor(scope): 重构范围

Motivation:
- <为什么重构>

Changes:
- <结构调整1>
- <结构调整2>

Behavior:
- <说明行为是否完全不变，或列出细微差异（如错误信息变更）>

Validation:
  Steps:
  - <回归验证步骤>
  Result:
  - <验证结论>
```

### 2.4 性能优化（perf）

```text
perf(scope): 优化点

Baseline:
- <优化前指标>

Optimization:
- <优化策略>

Result:
- <优化后指标>

Validation:
  Steps:
  - <压测/采样方法>
  Result:
  - <测量结论>
```

### 2.5 工程/构建（chore）

```text
chore(scope): 变更内容

Changes:
- <依赖或配置变更>

Reason:
- <升级/安全/兼容原因>

Impact:
- <对开发或运行的影响>

Validation:
  Steps:
  - <构建/启动验证步骤>
  Result:
  - <验证结论>
```

### 2.6 测试（test）

```text
test(scope): 测试变更摘要

Scenario:
- <覆盖的测试场景>

Coverage:
- <新增/调整的覆盖范围（函数、分支、行）>

Validation:
  Steps:
  - <运行命令>
  Result:
  - <测试通过结论、覆盖率变化>
```

### 2.7 文档（docs）

```text
docs(scope): 文档更新摘要

Background:
- <变更背景，如 API 变更、流程调整>

Audience:
- <目标读者，如内部开发者、外部接入方>

Changes:
- <新增/修改/删除的文档内容>
```

### 2.8 破坏性变更（!）

在 `type(scope)` 后加 `!`，正文必须包含 `BREAKING CHANGE:` 段落说明迁移路径。

```text
feat(api)!: 移除 v1 用户查询接口

Goal:
- 统一使用 v2 接口，清理历史兼容层

Implementation:
- 删除 /api/v1/users 路由及相关 handler
- v2 接口已包含全部原有字段

BREAKING CHANGE:
- /api/v1/users 不再可用
- 迁移方式：将请求路径改为 /api/v2/users，
  响应结构中 `name` 字段拆为 `firstName` + `lastName`

Validation:
  Steps:
  - 调用 /api/v1/users，确认返回 404
  - 调用 /api/v2/users，确认字段完整
  Result:
  - v1 路由已下线，v2 全量通过
```

## 3. UI 与非 UI 区分

### 3.1 为什么需要区分

- 便于发布说明快速筛选"用户可见变化"。
- 便于回滚时精准定位视觉/交互改动。
- 便于 AI 与评审工具做影响面分类。

### 3.2 判定规则

- **UI 变化**：用户可直接看到或感知的改动。
  - 例如：布局、样式、交互流程、按钮文案、入口位置。
- **非 UI 变化**：用户不可直接感知的改动。
  - 例如：接口、数据结构、性能、重构、测试、构建配置。

### 3.3 提交要求

- `scope` 必须体现改动面：`ui` / `api` / `db` / `core` / `build`。
- UI 提交正文必须包含 `UI:` 段落，写明页面/组件路径与可见变化。
- 混合改动（UI + 非 UI）优先拆为两个 commit：
  - `feat(ui):` 或 `fix(ui):`
  - `feat(api):` / `fix(db):` / `refactor(core):` 等
- 如确实无法拆分，使用联合 scope（如 `feat(ui+api):`），并在正文分段描述两侧影响。

### 3.4 UI 提交示例

```text
fix(ui): 修复数据库树在 pgsql 下函数分类不刷新

Problem:
- 左侧树函数数量与实际不一致

RootCause:
- 函数列表刷新后未触发对应分类区域重渲染

Fix:
- 调整函数列表刷新后的状态同步顺序
- 增加分类节点刷新触发条件

UI:
- 页面：数据库管理 / 左侧树
- 可见变化：展开函数分类后可即时看到最新函数数量与条目

Validation:
  Steps:
  - 连接 pgsql 后创建/删除函数并展开函数分类
  Result:
  - 树节点实时更新，未再出现数量不一致
```

### 3.5 非 UI 提交示例

```text
fix(core): 修复 PostgreSQL 切库后连接状态误判

Problem:
- 切库后偶发报"数据库未连接"

RootCause:
- 仅按数据库名判断切库完成，未覆盖连接句柄失效场景

Fix:
- 同库切换时若连接句柄失效则自动重连
- 统一数据库名归一化逻辑

Validation:
  Steps:
  - 多次切库并重复加载表/函数列表
  Result:
  - 未再复现"数据库未连接"报错
```
